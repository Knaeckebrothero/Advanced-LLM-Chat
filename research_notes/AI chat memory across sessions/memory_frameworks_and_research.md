# Long-term memory frameworks and research for LLM agents and chatbots (state as of 2026-11-01)

Evidence labels used below: **[peer-reviewed]** = paper accepted at a venue (ICLR/NeurIPS/ACL/EMNLP/TMLR); **[preprint]** = arXiv only; **[vendor]** = numbers or claims published by the company that sells the system; **[community]** = blog posts, audits or reverse engineering by third parties (often with their own commercial interest). GitHub figures were pulled from the GitHub API on 2026-11-01.

## 1. How each framework works (write path, storage, retrieval, update/forgetting), current status, license, self-hostability

### Takeaway
The field has split into (a) pipeline extractors that turn each conversation into facts or profiles (Mem0, Memobase, Supermemory, Honcho, Hindsight, MemOS, Mastra Observational Memory), (b) temporal knowledge graphs (Graphiti/Zep, Cognee), and (c) agent-edited files (Letta, which in March 2026 abandoned its own database memory tools for git-backed markdown files edited with bash, the Anthropic memory tool, basic-memory, EverOS). Of the Python/Postgres-friendly options, Honcho (AGPL), Hindsight (MIT) and Memobase (Apache, activity slowing) run on PostgreSQL; Graphiti needs a graph DB (Neo4j/FalkorDB/Neptune); Mem0's headline 2026 numbers come from its closed managed platform, not the OSS SDK.

**Mem0**
- Original (2025) pipeline [preprint, vendor]: on each new message pair, an LLM extracts candidate facts using a database-held conversation summary plus the last m=10 messages; for each candidate it retrieves the top s=10 similar memories and the LLM chooses ADD, UPDATE, DELETE or NOOP via a tool call; GPT-4o-mini was used — [Mem0 paper, arXiv 2504.19413](https://arxiv.org/html/2504.19413)
- Mem0g (graph variant): entity extractor + relationship generator produce triplets in Neo4j; a conflict detector and LLM resolver mark obsolete relationships "invalid rather than physically removed" — [Mem0 paper](https://arxiv.org/html/2504.19413)
- New algorithm (April 2026) [vendor]: "Single-pass ADD-only extraction -- one LLM call, no UPDATE/DELETE. Memories accumulate; nothing is overwritten"; agent-generated facts (confirmations, recommendations) stored with equal weight; entity linking; semantic + BM25 + entity matching run in parallel and fused (BM25/entities need `mem0ai[nlp]` + spaCy) — [Mem0 README](https://github.com/mem0ai/mem0)
- External graph store support was replaced by built-in entity linking; the `relations` field is gone and entity relationships "cannot be traversed directly" — [Mem0 blog, State of AI Agent Memory 2026 (updated 2026-10-10)](https://mem0.ai/blog/state-of-ai-agent-memory-2026)
- OpenMemory: local-first, MCP-compatible memory layer with a dashboard for Claude Desktop, Cursor, Windsurf, VS Code; hosted variant also offered — [Mem0 blog](https://mem0.ai/blog/state-of-ai-agent-memory-2026)
- Deployment: library (`pip install mem0ai`), self-hosted server (`docker compose up`, auth on by default), or cloud — [Mem0 README](https://github.com/mem0ai/mem0)
- Benchmark caveat in Mem0's own README: "Scores reflect Mem0's managed platform, which includes proprietary optimizations not available in the open-source SDK" — [Mem0 README](https://github.com/mem0ai/mem0)

**Letta / MemGPT**
- MemGPT's design (2023): fixed in-context "core memory" the agent edits with tools, plus out-of-context recall memory (conversation history) and archival memory (vector store), reached via function calls — [MemGPT paper, arXiv 2310.08560](https://arxiv.org/abs/2310.08560) (description from the well-known paper; not re-fetched this session). The legacy tool `core_memory_replace` is confirmed by Letta's 2026 deprecation notice — [Letta, "Our next phase" (2026-03-16)](https://www.letta.com/blog/our-next-phase)
- Letta 0.7.0 split work into a primary agent (user messages, tools, external memory search) and a sleep-time agent that edits in-context memory blocks in the background — [search summary of Letta docs/release notes](https://docs.letta.com/letta-code/memory)
- 2026-03-16 pivot: "Memory moves from specialized memory tools that edit memory in a database to generalized computer use tools like bash"; memory lives in git-backed context repositories ("MemFS"); "Legacy server memory tools like core_memory_replace will be removed"; "Server-side sleep-time agents will be replaced by a client-side subagent system"; tool rules deprecated, templates and the server filesystem deprecated by mid-April 2026 — [Letta, "Our next phase"](https://www.letta.com/blog/our-next-phase)
- Letta Code: MemFS is "a git-backed memory filesystem that they can inspect and edit", shared across the agent's conversations; "dreaming" subagents review recent conversations and update memory, triggered "after a set number of completed agent steps or when the context window is compacted"; optional second background review pass; agents on a Docker server fall back to the legacy memory-blocks system — [Letta docs, Memory & dreaming](https://docs.letta.com/letta-code/memory)

**Zep / Graphiti**
- Graphiti graph = episode subgraph (raw messages as "non-lossy data store"), semantic entity subgraph (entities + fact edges resolved against existing entities), community subgraph (label propagation clusters with summaries) — [Zep paper, arXiv 2501.13956](https://arxiv.org/html/2501.13956)
- Bi-temporal model: T′ (ingestion timeline: t′created, t′expired) and T (event timeline: tvalid, tinvalid); an LLM compares new edges with semantically related existing edges, and on contradiction sets the old edge's tinvalid to the new edge's tvalid; new information wins — [Zep paper](https://arxiv.org/html/2501.13956)
- Retrieval: cosine similarity on fact/entity/community fields, BM25 (Neo4j Lucene), BFS n-hop expansion; rerankers RRF, MMR, episode-mentions, node distance, cross-encoder ("highest computational cost") — [Zep paper](https://arxiv.org/html/2501.13956)
- Requirements: Neo4j 5.26, FalkorDB 1.1.2, Amazon Neptune (+OpenSearch), Kuzu 0.11.2 (deprecated); defaults to OpenAI; "works best with LLM services that support Structured Output (such as OpenAI, Anthropic, and Gemini)" — [Graphiti README](https://github.com/getzep/graphiti)
- Positioning (2026): "Neither is an agent memory product: Graphiti is a framework for building graphs, and Zep unifies, governs, and serves an enterprise's context"; Zep runs its own graph DB service (Konig) — [Graphiti README](https://github.com/getzep/graphiti)

**LangMem / LangGraph store**
- Memory types: semantic (collections of records, or a single "profile" document representing current state, updated in place), episodic ("preserves successful interactions as learning examples"), procedural (prompt rules refined through feedback) — [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- Hot path saving "adds perceptible latency to user interactions"; background ("subconscious") reflection after a conversation/inactivity avoids latency but updates are delayed; over-extraction reduces precision, under-extraction lowers recall; ranking combines similarity, importance and strength (recency/frequency of use) — [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- Hot-path tools `create_manage_memory_tool` / `create_search_memory_tool`; background memory manager; production storage via LangGraph `AsyncPostgresStore` — [LangMem README](https://github.com/langchain-ai/langmem)
- In Mem0's (competitor-run) LoCoMo test, LangMem search latency was p50 17.99 s / p95 59.82 s — [Mem0 paper](https://arxiv.org/html/2504.19413)

**A-MEM** [peer-reviewed, NeurIPS 2025]
- Zettelkasten-style: each new memory becomes a note with "contextual descriptions, keywords, and tags"; links are created to related historical notes; new notes "can trigger updates to the contextual representations and attributes of existing historical memories" (memory evolution) — [A-MEM, arXiv 2502.12110](https://arxiv.org/abs/2502.12110)

**MemOS**
- Unified add/retrieve/edit/delete memory API "structured as a graph"; self-hosted Docker stack = MemOS API + Neo4j + Qdrant; local plugin uses SQLite with hybrid FTS5 + vector retrieval, dedup and "tiered skill evolution (L1 traces / L2 policies / L3 world model)"; vendor claims 88.83 LoCoMo and 89.20 LongMemEval (2026-07-02) — [MemOS README](https://github.com/MemTensor/MemOS)

**Cognee**
- Builds a knowledge graph (entities, relationships, chunks) from documents, code and conversations; can extract with a local GLiNER model and local embeddings without any LLM key; imports from Mem0, Letta, Zep, Graphiti (COGX format) — [Cognee README](https://github.com/topoteretes/cognee)
- Open-core caveat: "Using Postgres as a graph store is currently released as a demo feature. The production-ready version is available as a licensed product" — [Cognee README](https://github.com/topoteretes/cognee)

**Supermemory**
- Extracts facts, builds user profiles (`profile.static` long-term facts, `profile.dynamic` recent context), "handles knowledge updates and contradictions, forgets expired information"; self-host via `npx supermemory local` or Docker (embedded graph engine, local `bge-base-en-v1.5` embeddings, optional Ollama e.g. gpt-oss:20b) — [Supermemory README](https://github.com/supermemoryai/supermemory)
- Vendor claim: "#1 on LongMemEval, LoCoMo, and ConvoMem"; on LongMemEval "95% Recall@15 while adding only ~720 tokens of context" (note: a retrieval recall metric, not end-to-end QA accuracy); publishes an open-source MemoryBench harness — [Supermemory README](https://github.com/supermemoryai/supermemory)

**Memobase**
- User-profile memory (topic / sub_topic / content, schema configurable) plus a user event timeline for temporal questions; explicitly not in the hot path ("buffer zones for the recent inserted blobs"); profile goes into the system prompt; FastAPI + Postgres + Redis, fully dockerized; v0.0.40 cut LLM calls per run from ~3-10 to a fixed 3 (−40-50% token cost); claims it "works similarly to the memory system behind ChatGPT" — [Memobase README](https://github.com/memodb-io/memobase)

**Honcho** (relevant to a therapist persona: user modeling)
- Store messages, Honcho "reason[s] in the background" (a deriver) and updates "peer representations"; exposes "Conclusions — what Honcho has extracted about a peer (deductive and inductive)"; observations stored as vector-embedded documents in collections keyed by `(observer, observed)` peer pairs; self-host needs PostgreSQL with pgvector (Redis optional); AGPL-3.0 — [Honcho README](https://github.com/plastic-labs/honcho)

**Hindsight**
- Four logical memory networks (world facts, agent experiences, synthesized entity summaries, evolving beliefs); operations retain / recall / reflect — [Hindsight paper, arXiv 2512.12818](https://arxiv.org/html/2512.12818v1); ACL 2026 System Demonstrations version — [ACL Anthology author page](https://aclanthology.org/people/nicolo-boschi/)
- Retain uses an LLM to extract facts, temporal data, entities, relationships, then normalizes into canonical entities and indexes; recall runs semantic, keyword, graph (entity/temporal/causal links) and temporal-range retrieval, merges with reciprocal rank fusion plus a cross-encoder reranker, trims to a token budget; background consolidation into "observations" that keep "supporting evidence with exact quotes and a proof count"; 25+ LLM providers incl. Ollama/llama.cpp; Docker with external PostgreSQL — [Hindsight README](https://github.com/vectorize-io/hindsight)

**Mastra Observational Memory** (TypeScript)
- Two background agents, an Observer and a Reflector, compress history into a dated observation log kept in context instead of retrieval; Mastra says this keeps the context window stable and cacheable; at launch observation ran synchronously and blocked the conversation, with async buffering announced afterwards — [Mastra research page](https://mastra.ai/research/observational-memory); [The Decoder](https://the-decoder.com/mastras-open-source-ai-memory-uses-traffic-light-emojis-for-more-efficient-compression/); [Mastra blog](https://mastra.ai/blog/observational-memory)

**File-based / product memory**
- Anthropic memory tool (`memory_20250818`): client-side; Claude issues view/create/str_replace/insert/delete/rename calls against a `/memories` directory that the application stores wherever it wants — [Claude docs, Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Claude.ai past-chat memory: the model calls `conversation_search` / `recent_chats` tools that search raw past chats ("no AI-generated summaries or compressed profiles—just real-time searches through your actual past chats") [community] — [Simon Willison (2025-09-12)](https://feeds.simonwillison.net/2025/Sep/12/claude-memory/); official help center: searches appear as visible tool calls, scoped per project, incognito excluded, memory saved "as a set of individual topics" — [Claude Help Center](https://support.claude.com/en/articles/11817273-use-claudes-chat-search-and-memory-to-build-on-previous-context)
- ChatGPT memory [community, reverse-engineered]: saved memories (user-visible fact list) injected into the system prompt each turn, plus a lightweight summary of recent conversations and distilled user insights; one analysis says no vector DB/RAG over history, others dispute — [llmrefs](https://llmrefs.com/blog/reverse-engineering-chatgpt-memory); [Gigazine (2025-12-26)](https://www.gigazine.net/gsc_news/en/20251226-reverse-engineered-chatgpt-memory-system); [r/MachineLearning thread](https://redlib.hbubli.cc/r/MachineLearning/comments/1kmri3v/d_reverseengineering_openai_memory)
- EverOS: memory stored as readable Markdown with SQLite + LanceDB indexes; offline reflection "merges episode clusters and refines profiles and skills between sessions" — [EverOS README](https://github.com/EverMind-AI/EverOS)

### Inferences
- Letta, the originator of agent-edited memory blocks, dropping its specialized DB memory tools for files + bash (March 2026) is strong industry corroboration of the developer's finding that "a knowledge base the agent can write to" beats bespoke memory APIs, at least with strong models.
- Mem0 moving from LLM-decided ADD/UPDATE/DELETE to ADD-only suggests the update-decision step was a source of errors (cf. Memory-R1's DELETE+ADD example in section 4), but ADD-only shifts conflict handling to retrieval/ranking; see the contradicting evidence on append-only stores in section 3.
- Letta's GitHub release cadence stalled at 0.16.8 (May 2026) while Letta Code became the flagship; the self-hosted Letta server is a risky dependency for a new integration.
- For this app, the frameworks that natively fit "Postgres only" are Honcho (AGPL: modifying and serving it obliges source release), Hindsight (MIT) and Memobase (Apache, slowing activity). All are separate services with their own LLM pipelines rather than libraries; none is "small".

### Gaps
- Exact Zep Community Edition deprecation date and Mastra's license were not verified this session.
- Mem0 versioning is unclear: the README links an "oss-v2-to-v3" migration guide while the latest Python tag is v2.2.1; whether the ADD-only algorithm is fully in the OSS Python SDK was not confirmed.
- MemGPT paper and Letta sleep-time compute paper details were not re-fetched; descriptions rely on well-known content and Letta's own 2026 notes.
- The Hindsight star count (57k) looks unusually high relative to its peers; it is reported as returned by the API, not checked further.

## 2. Taxonomy: working / episodic / semantic / procedural; profile memory; reflection and consolidation; forgetting and decay; conflict resolution

### Takeaway
2026 surveys frame memory as a write-manage-read loop along three axes (temporal scope, representational substrate, control policy). The weakest parts across all systems are consolidation (episodic→semantic transition), forgetting (mostly crude TTL/eviction or nothing) and conflict handling. The practical mechanisms with evidence behind them are temporal validity on facts (Graphiti), recency/source priority, a user profile document, and background reflection with evidence links.

### Cited Findings
- Survey framing: memory as a "write–manage–read loop"; the update function "is _not_ a simple append operation"; temporal scope = working, episodic, semantic, procedural; the hard problem is the "transition policy" from episodic records to semantic knowledge, and consolidation "is rarely automatic"; substrates = context-resident text, vector stores, structured stores, executable repositories, hybrids — [Memory for Autonomous LLM Agents, arXiv 2603.07670](https://arxiv.org/html/2603.07670v1) [preprint]
- Control policy spectrum: heuristic control (top-k, summarize every n turns: predictable but "blind to context"), prompted self-control (LLM calls memory tools, e.g. MemGPT; quality depends on instruction following), learned control (e.g. AgeMem trained with step-wise GRPO) — [arXiv 2603.07670](https://arxiv.org/html/2603.07670v1)
- Forgetting: MemoryBank uses Ebbinghaus forgetting curves (reinforce accessed memories, let others fade); in practice systems rely on "hard time-based expiration, storage-limit eviction, or nothing at all" — [arXiv 2603.07670](https://arxiv.org/html/2603.07670v1)
- Conflict resolution recommendations: temporal versioning (prefer newest), source attribution (user statements outrank agent inferences), contradiction detection, periodic consolidation; incorrect reflections "can persist and entrench errors", mitigated by contradiction checks, confidence decay, expiration — [arXiv 2603.07670](https://arxiv.org/html/2603.07670v1)
- Other 2026 surveys: "A Survey of Agent Memory in the Second Half" (axes substrate / cognitive mechanism / subject; accepted to TMLR) — [arXiv 2602.06052](https://arxiv.org/abs/2602.06052); "From Storage to Experience" (stages Storage → Reflection → Experience; ACL 2026 Findings) — [arXiv 2605.06716](https://arxiv.org/abs/2605.06716); governance-focused SSGM framework — [arXiv 2603.11768](https://arxiv.org/pdf/2603.11768); long-term memory security survey (a poisoned entry can be recalled across an indefinite number of future sessions) — [arXiv 2604.16548](https://www.alphaxiv.org/abs/2604.16548)
- Profile memory as a first-class type: LangMem "profiles" (single current-state document updated in place) vs "collections" — [LangMem guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/); Memobase topic/sub_topic profile + event timeline — [Memobase](https://github.com/memodb-io/memobase); Supermemory static vs dynamic profile — [Supermemory](https://github.com/supermemoryai/supermemory); Honcho deductive/inductive "conclusions" per observer/observed peer pair — [Honcho](https://github.com/plastic-labs/honcho)
- Bi-temporal conflict handling (Graphiti): contradicted edges are invalidated (tinvalid set), not deleted, preserving history — [Zep paper](https://arxiv.org/html/2501.13956); Mem0g likewise marks relations invalid — [Mem0 paper](https://arxiv.org/html/2504.19413)
- Reflection/consolidation implementations: Hindsight observations with exact-quote evidence and proof counts — [Hindsight README](https://github.com/vectorize-io/hindsight); Letta dreaming subagents — [Letta docs](https://docs.letta.com/letta-code/memory); Mastra Observer/Reflector — [Mastra](https://mastra.ai/research/observational-memory); EverOS offline episode-cluster merging — [EverOS](https://github.com/EverMind-AI/EverOS)
- Procedural memory: LangMem prompt optimization — [LangMem guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/); MemOS "L1 traces / L2 policies / L3 world model" and skills — [MemOS](https://github.com/MemTensor/MemOS); Letta: skills become "the primary way to package and reuse agent capabilities" — [Letta, Our next phase](https://www.letta.com/blog/our-next-phase)
- Forgetting as a safety issue: PersistBench identifies cross-domain leakage (memories injected where inappropriate) and memory-induced sycophancy — [PersistBench, arXiv 2602.01146](https://www.arxiv.org/abs/2602.01146) [preprint]; MemoryAgentBench finds most systems fail selective forgetting — [arXiv 2603.07670](https://arxiv.org/html/2603.07670v1)
- Privacy: most users were unaware of long-term memory; aggregation of harmless inputs can expose sensitive information; proactive user interaction to surface/resolve memories was preferred in a N=36 user study — [arXiv 2410.14931](https://arxiv.org/html/2410.14931v1); an audit of 179,057 ChatGPT conversations of 1,057 users argues persistent memory amplifies health re-identification risks — [arXiv 2609.14697](https://arxiv.org/pdf/2609.14697)
- Therapy-specific: SoulSpeak (dual short/long-term memory plus anonymization) improved relevance over a GPT-3.5 baseline (0.65 vs 0.41) — [arXiv 2412.02987](https://arxiv.org/html/2412.02987v1) [preprint]

### Inferences
- For a therapist persona the most useful types map as: episodic = per-session summaries with dates (the app's rolling summary is already half of this); semantic/profile = a curated client profile (stable facts, goals, recurring themes, what helped); procedural = persona-level notes on what approaches work for this user. Working memory is the existing context window.
- Temporal validity (valid_from / valid_to plus recorded_at) is the cheapest conflict mechanism worth borrowing; it needs only two or four timestamp columns, not a graph DB.
- Memory-induced sycophancy and cross-domain leakage are especially relevant for therapy: memories should be user-visible and editable/deletable, and scoped per persona.

### Gaps
- No empirical comparison of forgetting/decay policies on conversational assistants was found; the evidence is that current policies are crude.
- No therapy-chatbot study measuring cross-session memory outcomes (benefit or privacy harm) with modern LLMs was found.

## 3. Benchmarks and evidence: LoCoMo, LongMemEval and newer; vendor claims vs replications; competitiveness of simple baselines; cost and latency

### Takeaway
Headline numbers are mostly vendor-run and not comparable (different answer models, judges, top-k, and platform-only optimizations). LoCoMo is compromised (≈6.4% wrong answer keys, lenient judge) and LongMemEval_S fits in modern context windows. Simple baselines are strong: full context beat every memory system in Mem0's own 2025 paper, and a plain file + grep/search agent beat Mem0 on LoCoMo. Memory systems win mainly on cost/latency and on long horizons or weak models, and the 2026 independent work finds no single architecture dominates.

### Cited Findings

**Benchmarks**
- LoCoMo (Maharana et al., ACL 2024): up to 35 sessions and 300+ turns per conversation — [arXiv 2603.07670 survey](https://arxiv.org/html/2603.07670v1); full-context ≈26k tokens per conversation — [Mem0 paper](https://arxiv.org/html/2504.19413)
- LoCoMo audit [community, authors build a memory product]: 99 score-corrupting errors in 1,540 non-adversarial questions (6.4%), score ceiling ≈93.6%, 24 speaker-attribution errors; the gpt-4o-mini judge accepted 62.81% of intentionally wrong but topically adjacent answers (specific factual errors caught ~89%) — [Penfield Labs on DEV (April 2026)](https://dev.to/penfieldlabs/we-audited-locomo-64-of-the-answer-key-is-wrong-and-the-judge-accepts-up-to-63-of-intentionally-33lg); audit repo — [dial481/locomo-audit](https://hn.jakechampion.name/reader/https://github.com/dial481/locomo-audit); Category 5 (adversarial) excluded by convention due to missing answers — [Zep blog](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)
- LongMemEval [peer-reviewed, ICLR 2025]: 500 questions; abilities = information extraction, multi-session reasoning, temporal reasoning, knowledge updates, abstention; commercial assistants and long-context LLMs show "a 30% accuracy drop"; proposes session decomposition, fact-augmented key expansion, time-aware query expansion — [arXiv 2410.10813](https://arxiv.org/abs/2410.10813)
- Critique: LongMemEval_S is ~115k tokens per question; "The entire test corpus fits in a single context window for most current models", making it "a context window test, not a memory test" [community] — [Penfield Labs](https://dev.to/penfieldlabs/we-audited-locomo-64-of-the-answer-key-is-wrong-and-the-judge-accepts-up-to-63-of-intentionally-33lg)
- Newer: BEAM (ten memory abilities up to 10M tokens, ICLR 2026), MemoryArena (2026, multi-session interdependent tasks), MemoryAgentBench (retrieval, test-time learning, long-range understanding, selective forgetting), HaluMem, RealMem, LongMemEval-V2, STATE-Bench (Microsoft, 450 end-to-end tasks), DolphinBench (Mem0's own) — [Mem0 benchmarks library page (vendor)](https://mem0.ai/library/agent-memory/ai-memory-benchmarks-in-2026); [arXiv 2603.07670](https://arxiv.org/html/2603.07670v1)
- MemoryArena: models near-perfect on LoCoMo drop to 40-60%; swapping an active memory agent for long-context-only dropped task completion "from over 80% to roughly 45%" — [arXiv 2603.07670](https://arxiv.org/html/2603.07670v1)
- MemoryAgentBench: "No current system masters all four competencies"; most fail selective forgetting — [arXiv 2603.07670](https://arxiv.org/html/2603.07670v1)
- DMR (MemGPT's benchmark) is saturated: ~60 messages per conversation; full-conversation 98.0% vs Zep 98.2% (gpt-4o-mini) — [Zep paper](https://arxiv.org/html/2501.13956)

**Mem0 vs Zep vs Letta dispute (2025)**

**Independent / academic 2026 evaluations**
- "Are We Ready For An Agent-Native Memory System?" (2026-06-23) evaluated 14 systems (MemoChat, Mem0, MEM1, MemAgent, MemTree, Zep, Mem0g, Cognee, LightMem, SimpleMem, MemOS, MemoryOS, A-MEM, Letta) plus Long Context and Embedding RAG baselines on LoCoMo, LongMemEval, DB-Bench, LongBench: "no single architecture dominates"; graph-based methods handle updates most reliably while "append-only stores and fact-extraction plugins struggle with targeted overwrites"; fine-grained extraction hurt multi-hop (MemOS 25.5 vs 2.5 EM); long context fell from 42.6 to 19.0 between short and long LongBench buckets; embedding RAG fell from 37.1 to 7.4 F1 as the evidence gap widened; "localized maintenance is more cost-efficient than global reorganization"; stronger backbones raise scores but change rankings only modestly. - Survey view: "Long context is not memory"; "RAG-based agents beat pure long-context baselines across the board" though retrieval quality is the bottleneck; summarization suffers "summarization drift" — [arXiv 2603.07670](https://arxiv.org/html/2603.07670v1)

**Cost and latency**

- Per-query operation latency in the 2026 independent study: LightMem 3.67 s, MemTree 15.9 s, MemoryOS 28.6 s, Cognee 116.5 s, Zep 155.1 s; on LongBench total per query LightMem 17.3 s, MemTree 116.7 s, A-MEM 552.1 s — [arXiv 2606.24775](https://arxiv.org/html/2606.24775v1)

### Inferences
- Mem0's 2026 jump (71 → 92.5 on LoCoMo) coincides with a top_200 retrieval budget and ~7k tokens per query, about a quarter of an entire ~26k-token LoCoMo conversation; part of the gain is likely from retrieving much more context, and the numbers are from the closed platform.
- For a single user in a therapy app, the history over months probably far exceeds what full context can hold, but a curated profile plus dated session summaries is small enough to always include; retrieval over raw transcripts is then only needed for specific recall.
- Benchmarks reward factual QA recall; a therapist persona needs themes, emotional trajectories and what helped, which no benchmark measures. Benchmark rankings should therefore weigh less than design fit.
- The "full context ties at short horizon, structured memory wins at long horizon" pattern (Ground Truth First, Are We Ready, MemoryArena) supports a hybrid: always-in-context profile/summary + searchable archive.

### Gaps
- No independent, same-harness comparison of Mem0 v3 OSS, Hindsight, Honcho, Supermemory and Graphiti was found; Supermemory's MemoryBench and Mem0's memory-benchmarks are vendor harnesses.
- The independent 2026 study's excerpt did not include results for small or open-weight backbones.
- BEAM and MemoryArena details came through a vendor page and a survey, not their primary papers.

## 4. Agent-managed memory (model calls tools) vs pipeline-managed memory (background extraction); fit with weaker open models

### Takeaway
Agent-managed memory with simple file/search tools works very well for strong tool-using models, and the industry trend (Letta MemFS, Anthropic memory tool, Claude chat search) is toward it. But memory quality then tracks tool-calling skill, and open-weight models trail on file-navigation agent benchmarks (Kimi K2.5 57% vs 88-93% for top proprietary models, GLM-5 39%). Pipeline extraction is deterministic about *when* memory is written and runs off the hot path, but still needs reliable structured output from the extraction model. The common production pattern in 2026 is hybrid: a background job (on a chosen, reliable model) consolidates, and the conversational agent gets read (and optionally write) tools.

### Cited Findings
- Letta's file-memory LoCoMo agent needed tool rules forcing it to start with `search_files` and keep searching until it answered, because GPT-4o-mini is weaker; the agent was "only partially autonomous" — [Letta blog (2025-08-12)](https://www.letta.com/blog/benchmarking-ai-agent-memory)
- Whether an agent "remembers" depends on whether it knows when and how to call a tool; iterative agent-written queries beat single-hop retrieval — [Letta blog](https://www.letta.com/blog/benchmarking-ai-agent-memory)
- Letta leaderboard: "models that excel at tool use tend to do well in Letta. Conversely, models that struggle to call tools properly often perform poorly"; strong archival-memory models (e.g. Claude Haiku 3.5) "might overuse memory operations when unnecessary" — [Letta leaderboard docs](https://docs.letta.com/leaderboard); [Letta leaderboard blog](https://www.letta.com/blog/letta-leaderboard)
- Context-Bench Filesystem Suite (updated 2026-03-13): GPT-5.2-Codex 93%, GPT-5.4 89%, Claude Sonnet 4.6 88%, Claude Opus 4.6 84%, Gemini 3 Flash 82%, GPT-5-mini 67%, **Kimi K2.5 57%**, Claude Haiku 4.5 43%, **GLM-5 39%**, MiniMax M2.5 37%; Skills Suite task completion: DeepSeek Chat 75.33%, DeepSeek Reasoner 70.48%, GLM-4.6 65.90% vs GPT-5.2 85.31%; Qwen, Llama, Gemma, gpt-oss not listed — [Letta Context-Bench leaderboard](https://leaderboard.letta.com/)
- Community guidance: small Ollama models (<7B) have "poor tool calling" for Letta-style memory [community] — [Letta forum skill file](https://forum.letta.com/t/skill-md-for-letta/99)
- Hot path writes add "perceptible latency"; background formation avoids it but is delayed — [LangMem guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- Pipeline systems in production: Memobase ("we don't memoize users in hot path", buffer zones) — [Memobase](https://github.com/memodb-io/memobase); Honcho ("background reasoning is asynchronous") — [Honcho](https://github.com/plastic-labs/honcho); Mastra Observer/Reflector — [Mastra](https://mastra.ai/research/observational-memory); Letta dreaming subagents triggered after N steps or at compaction — [Letta docs](https://docs.letta.com/letta-code/memory)
- LLM-chosen update operations are error-prone without training: a vanilla system treats "adopted a second dog" as a contradiction and does DELETE+ADD, overwriting the first; Memory-R1 trains an 8B LLaMA-3.1 memory manager with PPO/GRPO on ADD/UPDATE/DELETE/NOOP from 152 QA pairs and reports F1 30.41 → 45.02 (numbers differ between versions) [peer-reviewed, ACL 2026] — [Memory-R1, arXiv 2508.19828](https://arxiv.org/html/2508.19828v5); [ACL Anthology](https://aclanthology.org/2026.acl-long.583/)
- Graph extraction pipelines depend on structured output: Graphiti "works best with LLM services that support Structured Output (such as OpenAI, Anthropic, and Gemini)" — [Graphiti README](https://github.com/getzep/graphiti)
- Pipeline extraction can run on small local models: Cognee extracts graphs with GLiNER without any LLM — [Cognee](https://github.com/topoteretes/cognee); Hindsight's 83.6% LongMemEval used a 20B open-weight backbone — [arXiv 2512.12818](https://arxiv.org/html/2512.12818v1); Supermemory local recommends Ollama gpt-oss:20b — [Supermemory](https://github.com/supermemoryai/supermemory)
- Survey's practical advice: start with a context-plus-retrieval pattern ("Pattern B"), instrument it, and move to learned tiered control only if data shows it helps; prompted self-control quality depends on instruction following — [arXiv 2603.07670](https://arxiv.org/html/2603.07670v1)
- Claude.ai's memory is agent-managed retrieval: the model decides to call `conversation_search`/`recent_chats`, which are "not invoked automatically on every request" [community] — [Manthan Gupta via scour.ing (2025-12-14)](https://scour.ing/@emschwartz/p/https://manthanguptaa.in/posts/claude_memory)

### Inferences
- For this app's mix (Anthropic/OpenAI plus Kimi, DeepSeek, GLM, Gemma from a homelab), pure agent-managed writing would make memory quality depend on whichever model a persona uses; Gemma-class and some open models will forget to write or write poorly. A background consolidation job pinned to one reliable catalog model (configurable) decouples memory quality from the chat model.
- Reads are more forgiving than writes: an always-injected profile/summary needs no tool call at all, so weak models still "remember" the essentials; a search tool then adds depth for models that use tools well.
- Writes from the hot path (an agent "remember this" tool) are still valuable for explicit user requests ("please remember that…"), which even weaker models handle when the trigger is obvious.
- This matches the developer's experience: the knowledge base the agent can write to is the right storage abstraction; the question is only who writes (agent, background job, or both).

### Gaps
- No benchmark directly measured memory-tool reliability for Gemma, Qwen or gpt-oss class models; the Context-Bench data covers Kimi, GLM, MiniMax and DeepSeek only.
- No head-to-head study of agent-managed vs pipeline-managed memory with the same model and data was found.

## 5. What a minimal Python + PostgreSQL implementation takes, and which pieces are worth borrowing

### Takeaway
Everything the strong systems do on the storage/retrieval side can be built in Postgres: pgvector + full-text search fused with reciprocal rank fusion (used by Hindsight, Graphiti, Mem0 v3, MemOS local), validity timestamps for changing facts (Graphiti), a profile document always in the prompt (Memobase/LangMem/Supermemory), dated session summaries (Mastra-style observation log), evidence links back to source messages (Hindsight), and an Anthropic-memory-tool-shaped file interface stored as rows. Several mature systems (Honcho, Hindsight, Memobase, LangGraph PostgresStore) already run on Postgres + pgvector, which shows the stack is sufficient; adopting one of them adds a separate service and its LLM pipeline.

### Cited Findings
- Hybrid retrieval patterns to copy: Hindsight merges semantic, keyword, graph and temporal retrieval "using reciprocal rank fusion and a cross-encoder reranking model, then trimmed ... to fit within the token limit" — [Hindsight README](https://github.com/vectorize-io/hindsight); Graphiti uses cosine + BM25 + BFS with RRF/MMR/cross-encoder rerankers — [Zep paper](https://arxiv.org/html/2501.13956); Mem0 v3 fuses semantic, BM25 and entity matching — [Mem0 README](https://github.com/mem0ai/mem0); MemOS local plugin uses "hybrid retrieval (FTS5 + vector), smart dedup" on SQLite — [MemOS README](https://github.com/MemTensor/MemOS)
- Postgres as a sufficient substrate: Honcho requires "PostgreSQL with the pgvector extension" (Redis optional) — [Honcho](https://github.com/plastic-labs/honcho); Memobase is FastAPI + Postgres + Redis — [Memobase](https://github.com/memodb-io/memobase); Hindsight runs with external PostgreSQL — [Hindsight](https://github.com/vectorize-io/hindsight); LangGraph's `AsyncPostgresStore` is the production store for LangMem — [LangMem README](https://github.com/langchain-ai/langmem); Cognee keeps "relational metadata, PGVector, and graph state" in one Postgres (demo; production version licensed) — [Cognee](https://github.com/topoteretes/cognee)
- Temporal validity fields (tvalid/tinvalid, t′created/t′expired) and invalidation instead of deletion — [Zep paper](https://arxiv.org/html/2501.13956)
- LongMemEval's indexing advice: decompose sessions into finer values, expand keys with extracted facts ("fact-augmented key expansion"), and use time-aware query expansion — [arXiv 2410.10813](https://arxiv.org/abs/2410.10813)
- Profile-in-prompt pattern: Memobase places profiles into the system prompt — [Memobase](https://github.com/memodb-io/memobase); ChatGPT reportedly injects saved memories into the system prompt each turn [community] — [llmrefs](https://llmrefs.com/blog/reverse-engineering-chatgpt-memory)
- File-shaped write interface: Anthropic's memory tool commands (view, create, str_replace, insert, delete, rename) over `/memories`, storage entirely up to the client — [Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool); Letta MemFS (git-backed markdown) — [Letta docs](https://docs.letta.com/letta-code/memory)
- Evidence/provenance: Hindsight observations keep exact quotes and a proof count — [Hindsight](https://github.com/vectorize-io/hindsight); in Ground Truth First, "injection resistance tracked whether provenance boundaries survived representation" — [arXiv 2607.21962](https://arxiv.org/abs/2607.21962)
- Maintenance strategy: localized maintenance beats global reorganization on cost; conservative merge beat delayed flushing — [arXiv 2606.24775](https://arxiv.org/html/2606.24775v1)
- Raw-transcript search is a viable read path on its own (Claude.ai searches actual past chats, no summaries) — [Simon Willison](https://feeds.simonwillison.net/2025/Sep/12/claude-memory/)
- Letta's dream trigger "when the context window is compacted" — [Letta docs](https://docs.letta.com/letta-code/memory)

### Inferences
- A minimal design that fits this codebase (inferred; not from a source):
  1. `memories` table: id, user_id, persona/scope, kind (profile | episode | fact | note), path-like key (for an Anthropic-memory-tool-style "file" view), content, embedding `vector(n)`, `tsvector` (GIN index), source message/conversation ids, recorded_at, valid_from, valid_to/superseded_by, confidence/source (user-stated vs inferred).
  2. Write path A (pipeline): when a conversation goes idle or the existing rolling-summary job runs, one structured-output call on a configurable catalog model produces (a) a dated session summary (episode) and (b) a patch to the persona's profile document, with candidate facts compared against top-k similar existing ones; supersede via valid_to instead of deleting.
  3. Write path B (agent): `memory` tool (view/create/str_replace/delete over the same rows; Anthropic's native tool on Claude, an equivalent JSON-schema tool for OpenAI-compatible models) for explicit "remember this" moments.
  4. Read path: always inject profile + the last few session summaries via the existing `with_instructions()` system-prompt tail; add a `search_memory` / `search_past_sessions` tool doing pgvector + FTS fused by RRF for deeper recall.
  5. Controls: user-visible memory page (edit/delete), per-persona scoping, opt-out, and no cross-persona leakage by default.
- Worth borrowing: Graphiti's validity timestamps, Hindsight's RRF + evidence quotes, Memobase/Supermemory's profile-plus-timeline split, Mastra's dated observation log idea (stable, cacheable prompt prefix), Anthropic's memory-tool command set, Letta's "consolidate at compaction" trigger (this app already has a compaction-like summary step at 80% of the window).
- Not worth a dependency for this app's scale: Graphiti (needs Neo4j/FalkorDB and structured-output models), MemOS (Neo4j + Qdrant), Cognee (Postgres graph mode is open-core demo), Letta server (deprecating server features). Honcho is the closest functional fit for therapist-style user modeling but is AGPL and a separate service; Hindsight (MIT, Postgres) is the strongest MIT option if a service is acceptable.

### Gaps
- No source measured the quality of a "profile + session summaries + hybrid search" design on LongMemEval/LoCoMo directly; its competitiveness is inferred from Mastra OM (summaries/observations), Letta's filesystem result and the full-context baselines.
- Embedding model choice for multilingual (German/English) memories, and pgvector index settings at this scale, were not researched.
